Implement undo/redo for orbit_state. Locate the existing `OrbitStore` base
class (`lib/src/orbit_store.dart`), the `Orbit` static container class
(`lib/src/orbit_container.dart`), and the existing `mutate()` /
`mutateAsync()` / `debugSnapshot()` methods before writing any code —
integrate with them rather than duplicating logic. This depends on the
already-implemented `batch()` feature but does NOT need to be
batch-aware (see "Explicitly out of scope" below).

## Step 1 — Rename `debugSnapshot()` to `snapshot()`

`OrbitStore.debugSnapshot()` currently powers `Orbit.observe`/`changeLog`
diffing. Rename it to `snapshot()` everywhere (declaration, all overrides,
all call sites including `_safeSnapshot()`), and use this single method
for both its existing purpose (debug/observe diffing) and the new undo
mechanism below. Update doc comments to describe both use cases. Do not
create a second separate snapshot method — one contract, one method.

## Step 2 — `Undoable` mixin

```dart
mixin Undoable on OrbitStore {
  /// Applies a previously captured snapshot (from [OrbitStore.snapshot])
  /// back onto this store's fields. Called by Orbit.undo()/redo() —
  /// never call this directly.
  void restore(Map<String, Object?> state);
}
```

Override `mutate<R>()` on this mixin (NOT a new method name — must
literally override the base class's `mutate`) so that:

1. Take `before = snapshot()` synchronously, before calling
   `super.mutate(action, label: label)`.
2. Run the actual mutation via `super.mutate(...)` — this must go through
   the real base implementation unchanged, so batching, `Orbit.observe`,
   and `changeLog` all continue working exactly as they do today.
3. After the mutation completes — for sync results, immediately after
   `super.mutate()` returns; for async results (`result is Future`),
   only after the returned Future resolves via `.whenComplete()`, same
   async-timing pattern already used in the `batch()` implementation —
   take `after = snapshot()` and push an entry onto the global undo stack
   via `Orbit._pushUndo(...)`.
4. This must work correctly whether `super.mutate()` throws (sync) or its
   returned Future completes with an error (async): push the undo entry
   in BOTH the success and error cases (state may have already partially
   changed before an error, and existing `OrbitMutation` recording already
   treats that as record-don't-drop; undo entries follow the same
   philosophy), then rethrow/propagate the original error unchanged.
5. Guard against reentrancy: if `Orbit._isRestoring` is true (see Step 3),
   skip snapshot-taking and stack-pushing entirely, but still call
   `super.mutate(action, label: label)` so the actual state change,
   notification, and batching/logging all still happen normally. Without
   this guard, `Orbit.undo()`/`redo()` calling `restore()` through
   `mutate()` would recursively push new undo entries for the undo/redo
   action itself, corrupting the stacks.

`mutateAsync()` on the base class internally calls `this.mutate(() =>
apply(result), ...)`, which virtually dispatches to this override — do
NOT write a separate `mutateAsync` override. Confirm this works via a
test (see Acceptance criteria).

## Step 3 — Global undo/redo stacks on `Orbit`

```dart
class OrbitUndoEntry {
  OrbitUndoEntry({
    required this.store,
    required this.before,
    required this.after,
    this.label,
  });

  final OrbitStore store; // must be an Undoable instance
  final Map<String, Object?> before;
  final Map<String, Object?> after;
  final String? label;
}
```

Add to `Orbit`:

```dart
static int undoStackLimit = 50;
static bool get canUndo => _undoStack.isNotEmpty;
static bool get canRedo => _redoStack.isNotEmpty;

static void undo();
static void redo();

/// Internal — called only from Undoable.mutate().
static void _pushUndo(OrbitUndoEntry entry);
```

Behavior:

- **One global stack**, not per-store — matches the decision that a
  single store scope is fine for now (no cross-store undo grouping
  needed), but the stack itself lives on `Orbit`, not on each store, so
  `Orbit.undo()` reads as "undo the last thing that happened anywhere."
- `_pushUndo`: if `Orbit._isRestoring` is true, no-op (belt-and-suspenders;
  the mixin already guards this, but don't rely on caller discipline
  alone). Otherwise append to `_undoStack`, trim from the front if length
  exceeds `undoStackLimit`, and **clear `_redoStack`** — a fresh mutation
  after an undo invalidates redo history, standard editor semantics.
- `undo()`: no-op if `_undoStack` is empty. Otherwise pop the last entry.
  If `entry.store` is disposed, drop the entry and do nothing further
  (do not push it to the redo stack — there's nothing meaningful to
  redo on a disposed store). Otherwise, set `Orbit._isRestoring = true`,
  call `entry.store.mutate(() => (entry.store as Undoable)
  .restore(entry.before), label: 'undo')` inside a try/finally that
  resets `_isRestoring = false`, then push `entry` onto `_redoStack`
  (uncapped — bounded naturally by how many times `undo()` was called).
- `redo()`: mirrors `undo()` exactly — pops from `_redoStack`, restores
  `entry.after` instead of `entry.before`, pushes back onto `_undoStack`
  (respecting `undoStackLimit` the same way `_pushUndo` does), same
  disposed-store handling, same `_isRestoring` guard.
- `Orbit.resetAll()` (or wherever existing global state is cleared, e.g.
  the same place `_globalBatchDepth`/`_globalPendingStores` already get
  reset — check `orbit_container.dart`) must also clear `_undoStack` and
  `_redoStack`.

## Explicitly out of scope / do not implement

- **No batch coalescing.** Each individual `mutate()` call inside an
  `Orbit.batch()` or `store.batch()` pushes its own separate undo entry.
  30 mutations in a batch = 30 undo entries, each independently undoable.
  `Undoable` requires zero awareness of batching — do not add any
  batch-depth checks to the mixin.
- **No per-mutation `undoable: false` opt-out.** Every `mutate()` call on
  an `Undoable` store is undoable; there is no flag to exclude specific
  calls.
- **No cross-store undo grouping.** `Orbit.undo()` reverts exactly one
  store's one mutation per call, even if other stores changed around the
  same time (e.g. via `watch()` cascades or `ComputedStore` recomputation
  triggered by the original mutation) — those are separate, independent
  entries on the same global stack if their stores also happen to be
  `Undoable`, not part of the same group.
- **Do not add an `isLoading` or any UI-transient concept** as part of
  this work.

## Acceptance criteria / tests to write

- A store mixing in `Undoable`: mutate it once, call `Orbit.undo()`,
  confirm fields match pre-mutation state and `notifyListeners()` fired
  during the undo (i.e. it went through `mutate()`/`restore()`, not a
  silent field reset).
- `Orbit.redo()` after an `undo()` restores the post-mutation state.
- A new `mutate()` call after an `undo()` clears `_redoStack` — confirm
  `Orbit.canRedo` is `false` afterward and `redo()` is a no-op.
- Async: `await store.mutate(() async { ... })` on an `Undoable` store —
  confirm the undo entry is only pushed after the awaited work completes,
  not before (same shape as the existing async-batch timing test).
- `mutateAsync()` on an `Undoable` store produces exactly one undo entry
  per call (via the `apply` callback's inner `mutate()`), not zero and not
  two.
- A mutation whose action throws (sync) or whose returned Future rejects
  (async) still pushes an undo entry reflecting whatever partial state
  change occurred, and the original error still propagates to the caller
  unchanged.
- Calling `Orbit.undo()` does NOT itself push a new entry onto
  `_undoStack` (reentrancy guard test — call undo(), then check
  `_undoStack` didn't grow by one from the undo action itself).
- `undoStackLimit`: push more than the limit, confirm the oldest entries
  are dropped and the stack never exceeds the limit.
- `Orbit.undo()`/`redo()` on a store that's been disposed in the meantime
  is a safe no-op (doesn't crash, doesn't push a bad entry to the other
  stack).
- `Orbit.resetAll()` clears both stacks.
- A plain (non-`Undoable`) store's `mutate()` calls never touch
  `_undoStack` at all — confirm no undo entries are created for stores
  that didn't opt in.
